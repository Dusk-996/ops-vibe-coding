# 流程问题定位

本页只处理九类流程采用问题，不是 Linux、Kubernetes 或生产故障修复手册。先定位 [Quick Start 当前阶段](01-quick-start.md)，再用只读检查区分缺输入、缺证据和需要人工决定的事项。目标是知道何时停手、带什么证据找谁；不承诺零错误或固定处理时长。

门禁与回退沿用 [Full Track](../workflows/full.md)，运行风险沿用 [Ops Readiness](06-ops-readiness.md)，证据沿用 [Harness](../harness/04-gates-and-evidence.md)。本页不以新的状态或规则替换它们。

| 编号 | 现象 | 对应阶段 |
|---|---|---|
| [T01](#t01) | Skill 未发现、同名冲突或版本不符 | 任何使用 Skill 的阶段 |
| [T02](#t02) | Skill、包、镜像或浏览器依赖获取失败 | 准备、S03、S10、S13 |
| [T03](#t03) | 缺 Spec、前置输入或人工确认 | S00、S02、S05–S10、S13–S14 |
| [T04](#t04) | Review 基点无效、空 diff 或只有未提交改动 | S11 |
| [T05](#t05) | 报告 PASS 与原始输出冲突 | S03–S04、S10–S14 |
| [T06](#t06) | 测试 SKIPPED、范围未验证 | S03–S04、S10、S12–S14 |
| [T07](#t07) | Restart UNKNOWN 或审计未确认 | 涉及该行为的 Spec、实现、审查、测试与验收 |
| [T08](#t08) | 换会话后不知当前阶段 | 任意会话交接点 |
| [T09](#t09) | 把业务验收、教学或局部通过当成可上线 | S12–S14 |

## 复制命令前先做这几件事

在**目标项目根目录**运行，先把 `<参数>` 换成实际路径、提交 ID 或日志文件。下面的 Git 命令在 PowerShell 与 Linux/macOS Shell 中相同；文件读取命令分开给出，别混用 Shell 语法。所有命令只检查现有本地材料，不安装依赖、不连接真实资源、不修复产品或生产配置。

```text
# PowerShell / Shell 通用；分行执行
git rev-parse --show-toplevel
git rev-parse HEAD
git status --short
```

读取某个批准记录、锁文件、报告或**已脱敏**原始输出时，选择当前终端对应的一组；不存在/不可读就是缺口，不能当作空文件或通过。

```powershell
# 仅在 PowerShell：先替换路径
Test-Path -LiteralPath '<项目内文件路径>'
Get-Content -LiteralPath '<项目内文件路径>'
```

```sh
# 仅在 Linux/macOS Shell：先替换路径
test -f '<项目内文件路径>'
cat -- '<项目内文件路径>'
```

求助时带：当前 S 编号、项目与输入修订、目标环境、允许范围、脱敏后的原始报错/命令/退出码、报告路径、已确认决定、缺口和下一步。不要贴 Secret、Token、kubeconfig 或包含敏感字段的完整日志。公共读取动作也须遵守 [权限与数据边界](../harness/06-tool-and-permission-boundaries.md)。

<a id="t01"></a>

## T01 Skill 未发现、冲突或版本不对

- **现象**：指令点名的 Skill 不可用；有多个同名 Skill；调用行为与项目要求不符。
- **阶段**：准备期及 S03–S13 中调用 Skill 的步骤。
- **只读检查**：对照 Skill Map 查看所需名称、来源和固定修订；查看当前运行时实际可发现的 Skill 清单及实际加载路径，读取所选 `SKILL.md` 核对名称与行为。若使用本地 Git 依赖检出，可执行：

```text
# PowerShell / Shell 通用；路径须替换为实际依赖检出目录
git -C "<Skill依赖检出目录>" rev-parse HEAD
git -C "<Skill依赖检出目录>" status --short
```

- **证据解读**：文件存在不等于当前会话已发现；检出 HEAD 正确也不能解释工作区修改，需两者同时核对。名称相同不代表来源或行为相同；只看到另一版本不能声称固定依赖已满足。
- **下一步 / 停手**：保存实际路径、修订与冲突项，停在当前步骤。由维护者指定唯一符合约定的来源和配置方式；不要静默调用另一份、复制外部实现进正式仓库或自动装最新版。修正后重查发现与实际加载结果，再继续原步骤。
- **求助角色**：项目维护人、Skill 维护人或本机运行时配置负责人；缺少指定角色时先由项目负责人指派。
- **权威文档**：[Skill Map](../references/skills.md)、[权限边界](../harness/06-tool-and-permission-boundaries.md)、[Full Track](../workflows/full.md)。

<a id="t02"></a>

## T02 依赖获取失败

- **现象**：Git/包/镜像/浏览器依赖获取超时、DNS/TLS 错误、代理异常、认证失败或找不到固定版本。
- **阶段**：准备期、S03 转换、S10 实现、S13 E2E。
- **只读检查**：读取已经保存的获取命令、错误、时间和退出码，核对目标域名/版本与项目锁文件或依赖记录。仅检查已安装工具，不触发下载：

```text
# PowerShell / Shell 通用；只运行当前步骤需要的项
git --version
node --version
git ls-files "*lock*" "*requirements*" "*Dockerfile*"
```

- **证据解读**：超时不能证明版本不存在；`401/403` 不能靠换版本解决；证书失败不能当作允许关闭校验。工具版本可读不代表包或浏览器已装好，锁文件存在不代表依赖已获取。
- **下一步 / 停手**：停止反复安装。由维护者核对批准的国内镜像、代理、可信替代地址或离线包，保留固定版本与校验信息；来源、权限或一致性未确认前不安装，不改全局源、不绕过 TLS，不把获取失败改写为测试通过。取得依赖后回原阶段重验。
- **求助角色**：依赖/网络环境负责人、项目维护人；凭证授权交对应资源负责人。
- **权威文档**：[Skill Map](../references/skills.md)、[权限边界](../harness/06-tool-and-permission-boundaries.md)、[Full Track](../workflows/full.md)。

<a id="t03"></a>

## T03 缺 Spec、输入或人工确认

- **现象**：找不到 Spec、Final 或批准记录；文件写着 Draft/待确认，却要求直接拆 Ticket、实现或验收。
- **阶段**：S02、S05–S10、S13–S14。
- **只读检查**：用页首对应终端的命令读取目标步骤列出的输入、批准记录和 handoff；逐一核对文件是否存在、修订是否相符、谁确认了什么。把当前输入与 Artifact Map 及 Full Track 同阶段的 Input 对照，不仅检查文件名。
- **证据解读**：存在 Spec 不等于已批准；有 Final 文件但关键约束仍未知不能作有效定稿；教学批准和 AI 的“用户应该同意”都不是你的项目批准。可找到文字描述也不代表 seam 或验收条件可测试。
- **下一步 / 停手**：停止依赖缺失输入的后续动作，列缺项及受影响范围。回对应原型审核、Grill、Spec 审核或测试计划批准点补齐；无法测试就回 Spec 的 seam/验收条件。可继续整理不依赖该决定的待审材料，但不伪造批准，不让 AI 自行补关键事实。
- **求助角色**：产品意图找真实使用者，部署/安全/可靠性约束找指定负责人，Spec/验收找范围与风险确认人，测试权限找环境及测试批准人。
- **权威文档**：[Full Track](../workflows/full.md)、[Artifact Map](../references/artifacts.md)、[会话生命周期](../harness/03-task-and-session-lifecycle.md)。

<a id="t04"></a>

## T04 Review 基点无效、空 diff 或未提交

- **现象**：基点无法解析；报告称无差异；实际改动只在工作区/暂存区，但报告声称覆盖了实现。
- **阶段**：S11 Code Review。
- **只读检查**：从项目已确认记录取得固定 base 和目标 head，替换下列参数；检查每条结果，不把第一条失败后其他命令的输出拼成成功：

```text
# PowerShell / Shell 通用；此处仅检查，不创建提交
git rev-parse --verify "<BASE提交>^{commit}"
git rev-parse --verify "<HEAD提交>^{commit}"
git log -5 --oneline
git diff --stat "<BASE提交>" "<HEAD提交>"
git diff --name-status "<BASE提交>" "<HEAD提交>"
git status --short
git diff --stat
git diff --cached --stat
```

- **证据解读**：两端可解析只证明提交存在，还要核对它们是否是批准范围。已提交 diff 为空时没有本次审查对象；工作区、暂存区或未跟踪文件不在该两提交差异中。`status` 中 `??` 表示未跟踪，不能因 `git diff` 没显示就忽略。
- **下一步 / 停手**：停止审查并列清楚缺口，不发“无问题/通过”报告。让维护者确定比较点和目标范围；尚未提交时按项目已有授权另行准备提交，再对确定修订重跑。不要为凑差异自动提交、造一个基点或静默改用工作区审查。
- **求助角色**：代码审核人、分支/提交负责人、项目维护人。
- **权威文档**：[Full Track §11](../workflows/full.md)、[Skill Map 中 code-review](../references/skills.md)、[证据规则](../harness/04-gates-and-evidence.md)。

<a id="t05"></a>

## T05 报告 PASS 与原始输出冲突

- **现象**：报告写 `PASS`，日志却有 `FAIL`、非零退出码或根本没有对应执行；截图/版本/环境也可能对不上。
- **阶段**：S03–S04、S10–S14 的验证及审查。
- **只读检查**：按页首读取方式逐项打开报告、原始 stdout/stderr、退出码记录、命令、输入修订、环境与执行时间；对照该次证据索引。不要此时重新执行可能有副作用的命令，也不要用当前终端 `$?` 或退出码猜测历史运行结果。
- **证据解读**：报告摘要不能覆盖原始失败；若日志属于另一修订或另一个环境，先记录关联错误，不选最乐观的材料。没有保留退出码就属于该证据缺口，不能补写 `0`；静态检查通过也不能推出运行成功。
- **下一步 / 停手**：拒绝沿用冲突结论，保留原报告和原始结果，登记冲突、影响范围及责任人。先核实来源，再在明确授权和环境中补做必要验证、另记结果；相关门禁按权威规则重评，不能覆盖旧结果或继续依赖该 PASS。
- **求助角色**：原报告执行者、证据复核人及受影响门禁审核人；风险决定交有权风险负责人。
- **权威文档**：[证据规则](../harness/04-gates-and-evidence.md)、[Full Track](../workflows/full.md)、[Ops Readiness](06-ops-readiness.md)。

<a id="t06"></a>

## T06 测试 SKIPPED 或范围未验证

- **现象**：缺应用、环境、身份、数据、浏览器或权限，测试写 `SKIPPED`；控制写 `NOT_VERIFIED`；只有示例命令没有执行结果。
- **阶段**：S03–S04、S10、S12–S14。
- **只读检查**：读取执行计划、批准范围、报告的环境限制和原始输出；逐条对照 Spec 验收范围，找出哪些执行过、哪些没有执行及原因。若是示例，检查顶部是否标明教学/未实际执行；用 [教学 E2E 报告](../examples/kubernetes-deployment-restart/09-e2e/test-report.md) 理解记录结构即可。
- **证据解读**：`SKIPPED` 是未执行，`NOT_VERIFIED` 是证据不足，均不等于 `PASS`。`NOT_APPLICABLE` 需要真实不适用理由，不能用来隐藏无法验证。文档写有测试步骤不等于跑过测试，本轮局部采用验证不替完整应用、生产或恢复验证。
- **下一步 / 停手**：记录原因、影响、缺什么证据、谁补齐和重验条件，停止依赖该缺口的放行。由相关人补环境或权限，在批准范围重验；是否影响阶段结论按 Full Track、对应阶段文档与证据规则判断，不自行降级或一律改为通过。
- **求助角色**：测试负责人、测试环境/数据/权限负责人，以及对应门禁审核人。
- **权威文档**：[Full Track](../workflows/full.md)、[证据规则](../harness/04-gates-and-evidence.md)、[E2E 与人工验收](07-e2e-and-human-acceptance.md)。

<a id="t07"></a>

## T07 Restart UNKNOWN 或审计未确认

- **现象**：Restart 提交超时或响应丢失，状态为 `UNKNOWN`；可能发生了外部变更，但最终审计是否持久化尚未确认。
- **阶段**：Restart 行为相关的 S08 Spec、S10 实现及 S11–S14 审查、测试、验收。
- **只读检查**：先保存原操作 ID、目标（集群/命名空间/Deployment 及可用身份标识）、提交时间、原始响应和已有证据路径。由项目事先指定的核验人，在已有只读权限内关联操作记录、审计记录与目标状态证据；本页只读取已有脱敏导出，不提供真实集群查询、补写或解锁命令。未指定核验人时先由项目负责人指派。
- **证据解读**：`UNKNOWN` 表示可能已执行，不能当作肯定失败；缺最终审计也不能证明没有外部变更。目标当前健康不能独自证明本次请求未执行或已经完成。按 Restart Spec，`SUBMITTED` 只表示提交与最终审计持久化达到约定，不代表 rollout 完成或业务恢复。
- **下一步 / 停手**：**停止重复提交，不换操作 ID 再试，不自动重试或释放目标占用。** 将原 ID 与证据交指定核验人；只读取证之后，任何补记、审计确认或释放占用，均由项目指定的有权人员批准、具备权限的维护者按项目程序处理，证据仍不明时保持阻断。本仓库描述的是教学契约与角色责任，没有提供可直接使用的恢复工具或接口。
- **求助角色**：指定核验人/管理员负责只读取证；有权批准人决定后续处置；有权维护者负责获批后的受控处理。新人和 AI 不得自行兼任未获授权角色。
- **权威文档**：[Restart Spec](../examples/kubernetes-deployment-restart/05-spec/deployment-restart.spec.md)、[Restart 架构](../examples/kubernetes-deployment-restart/04-architecture/stack-selection.md)、[Ops Readiness](06-ops-readiness.md)、[权限边界](../harness/06-tool-and-permission-boundaries.md)。

<a id="t08"></a>

## T08 新会话不知阶段

- **现象**：AI 重新选架构、重复执行操作、同时做多个 Ticket，或把上一段聊天中的“已完成”当事实。
- **阶段**：任何会话交接点，尤其 S10 的一个 Ticket 一个会话。
- **只读检查**：读目标项目 `AGENTS.md` 索引、最新 handoff、当前 Ticket、批准 Spec、必要 ADR 和门禁记录；用页首 Git 命令核对当前修订/工作区，打开交接引用的原始证据，确定最新有依据的阶段及未通过门禁。
- **证据解读**：聊天摘要与交接标题不替代证据；缺文件、输入修订不同或“已完成”无原始结果时，不能继承为通过。文件时间较新也不必然代表有效批准。并发或旧任务的证据不能直接归给当前 Ticket。
- **下一步 / 停手**：使用 [现有 handoff 模板](../harness/examples/handoff.example.md)，补齐当前阶段、一个 Ticket、输入修订、证据、阻断、指定责任人与下一步，交维护者核对后续当前任务。无依据部分保留待核验，不自动重做外部操作；若涉及未知结果按 T07 停手。
- **求助角色**：上一会话执行者、Ticket 负责人、项目维护人；权限或操作结果找对应指定核验人。
- **权威文档**：[会话生命周期](../harness/03-task-and-session-lifecycle.md)、[Context Engineering](04-context-engineering.md)、[证据规则](../harness/04-gates-and-evidence.md)。

<a id="t09"></a>

## T09 业务验收不等于上线

- **现象**：业务方说“接受”、教程报告或局部测试通过，就要求 AI 直接部署，或宣称具体产品生产就绪。
- **阶段**：S12–S14，以及从本方法论转入实际项目发布时。
- **只读检查**：读取验收对象与范围、产品修订、Ops 报告及原始证据、测试覆盖/跳过项、未关闭风险、部署/备份/验证/回滚方案和生产变更权限记录；用当前修订与被审修订比较，核对是否有影响分析。只读文件，不执行部署或生产验证命令。
- **证据解读**：方法论说明或配套模板通过不替具体产品放行；教学、静态、局部调用、运行验证不能互相冒充。人工业务接受也不能补出缺失的生产权限、关键控制证据、恢复验证或变更审批。旧证据是否仍有效要有范围及影响分析依据。
- **下一步 / 停手**：停止未获授权的发布与生产操作；把缺失的产品证据、风险决定、部署影响、备份/验证/回滚及权限交给相应负责人。按 Full Track 回到受影响阶段补齐，按目标项目发布程序决定。没有该产品运行与恢复证据时明确保留限制，不能让 AI 宣布生产可用。
- **求助角色**：业务验收人负责价值判断，有权风险负责人决定风险，发布/变更批准人和系统维护人负责生产处置；角色必须由项目指定。
- **权威文档**：[Full Track §12–14 及回退](../workflows/full.md)、[Ops Readiness](06-ops-readiness.md)、[E2E 与人工验收](07-e2e-and-human-acceptance.md)、[权限边界](../harness/06-tool-and-permission-boundaries.md)、[证据规则](../harness/04-gates-and-evidence.md)。
