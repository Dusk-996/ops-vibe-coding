| 编号 | 问题 | 用户确认答案 | 对架构与实现的影响 |
|---|---|---|---|
| **Q1** | 内存与 CPU 检测机制 | **A：多驱动可插拔采集引擎** | 区分“静态资产登记”与“动态指标检测”；后端内置独立 `collector` 模块，支持 `local`（本机真实采集）、`ssh`（远程 Linux 白名单只读命令采集，带超时与错误记录）、`mock`（自动化测试替身）三种驱动 |
| **Q2** | 前后端技术栈 | **A：前端 React（Vite）+ 后端 Python（FastAPI）** | 前端 Vite + React 18（保真还原已批准的双页原型）；后端 Python 3.11 + FastAPI |
| **Q3** | 存储与运行实例形态 | **A：单实例 + 内置 SQLite** | 单实例运行，进程内定时调度器 + 进程防并发锁；SQLite 单文件存储，保留连接串扩展位便于日后迁 PostgreSQL/MySQL |
| **部署阶段边界** | 生产部署方案时机 | **延后至 P6 专属部署阶段** | P1–P5 专注应用原型、前后端实现与真环境全面测试，不提前编写容器/服务编排文件；待 P5 测试全过后再进入 P6 设计与验证生产部署形态 |
| **交付顺序约定** | 前后端实现验收顺序 | **先完成并启动前端 → 用户打开确认通过 → 再开发后端** | P4 拆为两个显式验收子阶段：`P4a 前端实现与实机启动验收`（你亲眼看通后再进下一步）→ `P4b 后端采集引擎/API 实现与全量联调验收` |
